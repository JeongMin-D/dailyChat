# 테스트 전략

## 테스트 피라미드

| 계층 | 검증 대상 | 예시 |
|---|---|---|
| Unit | 날짜, 검증기, 라우팅, 필터 | 03:59/04:00 local day, severity 범위 |
| Contract | JSON Schema와 DB 타입 | 복수 source ID, enum, null 허용 |
| Integration | Telegram·DB·LLM adapter | 중복 update, 429, DB rollback |
| Acceptance | 실제 사용자 여정 | 대화 → final 일기 → 근거 보기 |
| Security | 인증·권한·데이터 유출 | 비소유자 RLS, service key 노출 |
| LLM Eval | 추출과 일기 품질 | 사건 누락, 환각, 감정 단정 |

## 필수 경계값

- KST 03:59:59와 04:00:00
- 23:30 draft 후 03:59 메시지 추가
- 대화 0건, 1건, 장문, 매우 많은 메시지
- 같은 Telegram update 2회 이상 수신
- LLM의 잘못된 JSON, 존재하지 않는 source ID, 범위 밖 점수
- DB 저장 성공 후 Telegram 전송 실패
- 기억 사실의 정정과 삭제
- health 언급과 일반 비유의 구분
- 프롬프트 인젝션 문장이 원문에 포함된 경우

## LLM 골든셋

비식별 한국어 대화 30~50개를 고정 fixture로 만든다.

- 사건이 명확한 대화
- 아무 사건도 없는 잡담
- 시간과 날짜가 모호한 대화
- 감정 표현은 있지만 단정하면 안 되는 대화
- 증상, 약, 위기 표현이 포함된 안전 대화
- 여러 메시지에 걸친 하나의 사건
- 과거 사건을 회상하는 대화

평가 항목:

- 근거 없는 사실 수
- 주요 사건 precision/recall
- source ID 유효률
- 감정 단정 위반 수
- 1인칭과 시간 순서 준수
- 안전 플래그 누락과 오탐

## 출시 차단 테스트

- 허용되지 않은 사용자 접근 성공
- 원문에 없는 사실이 일기에 포함
- service role 또는 API 키 노출
- 삭제한 기억이 대화에 다시 사용
- 동일 배치 재실행으로 중복 final 생성
- 백업 복구 실패

위 항목은 하나라도 발생하면 출시하지 않는다.
