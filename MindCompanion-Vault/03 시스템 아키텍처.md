# 시스템 아키텍처

## 권장 구조

```text
Telegram
   │ webhook
   ▼
Bot Gateway / Agent Runtime
   ├─ 사용자 허용 목록 검사
   ├─ 메시지 멱등 저장
   ├─ 대화 컨텍스트 구성
   ├─ LLM Provider 호출
   └─ Telegram 응답
   │
   ├──────────────► Supabase PostgreSQL
   │                 ├─ 원문 및 구조화 데이터
   │                 ├─ 기억 원장
   │                 ├─ 작업 실행 상태
   │                 └─ 감사 가능한 근거 연결
   │
Scheduler / Worker
   ├─ 야간 추출
   ├─ 일기 생성·확정
   ├─ 기억 후보 처리
   └─ 알림 재시도
   │
   ▼
Groq LLM Provider

Next.js Dashboard
   ├─ Supabase Auth
   ├─ RLS 기반 읽기/사용자 수정
   └─ 서버 전용 관리 작업
```

## 컴포넌트 책임

| 컴포넌트 | 책임 | 가지면 안 되는 것 |
|---|---|---|
| Bot Gateway | 인증, 수신, 즉시 저장, 응답 | 장시간 야간 작업 |
| Agent Runtime | 말투, 기억 검색, 대화 컨텍스트 | 데이터베이스 원본을 덮는 별도 진실 |
| Worker | 추출, 일기, 기억 후보, 재시도 | 공개 인터넷 요청의 직접 진입점 |
| LLM Provider | 요청/응답 표준화, 구조화 출력, 사용량 | 제품 정책 결정 |
| Supabase | 데이터 원장, RLS, 조회 | service role의 브라우저 노출 |
| Dashboard | 조회, 피드백, 사용자 수정 | 무제한 관리자 권한 |

## Source of Truth 확정안

- 메시지·구조화 기록·일기·작업 상태: Supabase
- 장기 기억: Supabase의 버전/근거가 있는 기억 원장
- `MEMORY.md`, `USER.md`: Agent가 빠르게 읽는 **생성된 투영본**
- 프롬프트: 저장소에서 버전 관리
- 비밀키: 배포 환경의 secret store

이 방식은 [[decisions/ADR-003 장기 기억 원장]]에서 확정했다. “잊어줘”, 기억 수정, 변경 이력, Web 관리 화면은 Supabase 원장을 기준으로 처리하며 투영 충돌 시에도 DB가 우선한다.

## 권장 모듈 경계

```text
apps/
  bot/                 # Telegram adapter와 webhook
  dashboard/           # Next.js UI와 서버 경계
services/
  conversation/        # 컨텍스트와 응답 오케스트레이션
  extraction/          # events/mood/health schema
  diary/               # 생성, 검증, 버전, 전달
  memory/              # 후보, 승인, 수정, 투영
  search/              # 날짜/키워드 조회
  llm/                 # provider interface와 Groq adapter
workers/                # 예약 작업과 재시도
packages/
  contracts/           # 공유 schema와 타입
  observability/       # 로그, metric, trace context
database/
  migrations/          # 순서가 있는 DB 변경
tests/
  fixtures/            # 비식별 골든셋
  integration/
  acceptance/
```

## 배포 단위

MVP에서는 복잡한 마이크로서비스 대신 다음 3개로 충분하다.

1. Bot/Worker가 함께 있는 서버 런타임
2. Next.js Dashboard
3. Supabase

서비스 내부 모듈 경계는 유지하되 독립 배포는 실제 병목이 확인된 뒤 분리한다.
