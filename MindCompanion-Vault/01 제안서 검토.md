# 제안서 검토

## 결론

제안서는 제품 목표, MVP 기능, 안전 원칙, 기본 스키마까지 갖춰져 있어 개발 출발점으로 충분하다. 다만 현재 문서 그대로 구현하면 모델 선택, 하루 마감, 기억의 원본, 데이터 근거 연결에서 서로 다른 규칙이 충돌한다. 따라서 기능을 넓히기 전에 **대화 → 저장 → 야간 처리 → 일기 전달**의 한 줄짜리 수직 슬라이스를 먼저 완성하는 구성이 적합하다.

## 잘 정의된 부분

- Telegram 대화를 별도 입력 폼 없이 기록으로 전환한다는 가치가 명확하다.
- 단일 사용자와 텍스트 대화로 MVP 범위를 제한했다.
- 원문 기반 일기, 감정 단정 금지, 의료 안전 원칙이 분명하다.
- `messages`, `events`, `mood_entries`, `health_entries`, `diaries`로 핵심 데이터가 분리돼 있다.
- RLS, 허용 Telegram ID, 비밀키 비노출이 초기 요구사항에 포함돼 있다.
- LLM 공급자 추상화와 구조화 출력 전략이 확장에 유리하다.

## 개발 전 반드시 해소할 충돌

| 우선순위 | 항목 | 현재 상태 | 권장 결정 |
|---|---|---|---|
| P0 | LLM 모델 | 제안서는 Groq GPT-OSS, 야간 프롬프트는 Claude | MVP는 Groq로 통일하고 모델명은 환경설정으로 분리 |
| P0 | 하루 마감 | 경계는 04:00, 일기는 23:30 생성 | 23:30은 draft, 04:05에 전날 final 또는 04:05 단일 생성 |
| P0 | 기억 원본 | OpenClaw Memory가 원본, Supabase는 미러 | Supabase를 감사 가능한 기억 원장으로 두고 Agent용 파일은 투영본으로 권장 |
| P0 | 이벤트 근거 | 스키마는 `message_id` 하나, 프롬프트는 복수 ID | 연결 테이블로 다대다 관계 구성 |
| P0 | 안전 플래그 | 프롬프트 출력에는 있으나 저장 위치 없음 | 야간 실행/일기 메타데이터에 저장하고 알림 정책과 연결 |
| P1 | Web 백엔드 | Next.js만 제시되고 쓰기 경계가 불명확 | 브라우저는 사용자 세션+RLS, service role은 서버 런타임에만 배치 |
| P1 | 자연어 검색 | 1차 MVP와 향후 벡터 검색이 혼재 | MVP는 날짜·키워드·trigram, 의미 검색은 후속 단계 |
| P1 | 일기 버전 | 재실행 규칙은 있으나 멱등성 키가 없음 | `day + pipeline_version + input_hash` 기준 재실행 정책 정의 |

## 빠진 비기능 요구사항

- 처리 보장: Telegram webhook 재전송과 중복 메시지 처리
- 장애 복구: LLM 실패, DB 실패, Telegram 발송 실패의 재시도 정책
- 데이터 수명: 원문·건강·기억 데이터의 보존 및 완전 삭제
- 관측성: 요청 ID, 실행 ID, 모델·토큰·지연·비용 기록
- 품질 기준: 추출 정확도와 일기 환각률의 합격선
- 마이그레이션: 스키마 버전 관리와 롤백 절차
- 백업 검증: 백업 생성뿐 아니라 실제 복구 훈련
- 프롬프트 버전: 어떤 일기가 어떤 프롬프트로 만들어졌는지 추적

## 범위 조정 제안

### 1차 출시 필수

- 허용 사용자만 Telegram 대화
- 원문 메시지의 멱등 저장
- 하루 단위 이벤트·기분·건강 추출
- 근거가 연결된 일기 생성과 Telegram 전송
- 기억 후보 검토·수정·삭제
- 날짜별 일기/타임라인/키워드 검색
- RLS, 비밀 관리, 백업·복구

### 출시 이후

- 모델 자동 라우팅 최적화
- 임베딩 기반 의미 검색
- 주간·월간 회고
- 고급 그래프와 통계
- 능동 체크인 자동화
- 음성·사진·다중 사용자
