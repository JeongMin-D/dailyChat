# 작업과 알림 원장

## 분리 원칙

야간 일기 생성 성공과 Telegram 전송 성공은 별도 상태다. 일기와 근거를 한 트랜잭션으로 저장한 뒤 outbox를 등록하고, 전송 Worker가 독립적으로 claim·재시도한다.

```text
job_run: queued → running → succeeded | retryable_failed | failed
notification: pending → sending → sent | retryable_failed | failed
```

공유 애플리케이션 계약은 `packages/contracts/src/job-contract.js`, DB 구현은 `database/migrations/0005_job_runs_notification_outbox.sql`이다.

## Job run

기존 `day + pipeline_version + input_hash` 멱등 identity를 유지한다. C04는 다음 운영 필드를 보강했다.

| 필드 | 의미 |
|---|---|
| `available_at` | 첫 실행 또는 재시도가 가능한 시각 |
| `updated_at` | claim과 상태 변경의 마지막 시각 |
| `attempt` | 성공한 claim 횟수 |
| `started_at` | 현재 attempt 시작 시각 |
| `finished_at` | succeeded/failed terminal 완료 시각 |

`claim_job_run(id)`은 due 상태의 queued/retryable_failed를 running으로 바꾸고 attempt를 증가시킨다. running 상태가 5분 이상 갱신되지 않으면 중단된 Worker로 보고 다시 claim할 수 있다. 같은 활성 작업의 즉시 중복 claim은 false를 반환한다.

## Notification outbox

outbox에는 사용자 원문이나 일기 본문을 넣지 않는다. 다음 참조·전송 메타데이터만 저장한다.

- 생성 작업 `job_run_id`
- 보낼 일기 `diary_id`
- channel과 notification type
- Telegram `recipient_chat_id`
- 상태, attempt, 재시도 가능 시각
- 고유 `idempotency_key`
- 성공 시 provider message ID와 sent 시각
- 실패 시 안정적인 error code

`(diary_id, channel, notification_type)`과 `idempotency_key`를 각각 unique로 제한한다. 같은 final 일기를 재시도할 때 새 outbox 행을 만들지 않고 기존 행의 상태와 예약 시각을 갱신한다.

## Claim과 재시도

`enqueue_diary_notification(job_run_id, diary_id)`은 succeeded 일기와 운영 `settings.telegram_chat_id`를 확인해 같은 알림을 한 번만 등록한다. safety none·concern은 `daily_diary`, urgent는 `safety_guidance`로 라우팅한다. `claim_diary_notification(id)`은 pending/retryable_failed 중 due인 행을 sending으로 바꾸고 attempt를 증가시킨다. 일기 본문은 outbox에 저장되지 않으며 urgent claim은 diary title과 block을 반환하지 않는다.

429·일시적 5xx·네트워크 오류는 최대 5번까지 지수 backoff로 `retryable_failed`에 예약한다. Telegram `retry_after`가 더 길면 그 값을 우선하고 DB는 지연을 최대 86,400초로 제한한다. 401·403과 그 밖의 4xx, 또는 최대 attempt 도달은 `failed`로 끝낸다. 성공은 Telegram `message_id`와 `sent_at`을 기록한다.

외부 전송은 exactly-once를 보장할 수 없다. Telegram 성공 응답을 받은 뒤 DB 기록 전에 프로세스가 종료되면 다시 보낼 가능성이 있으므로, provider message ID와 구조화 로그로 불확실 구간을 추적한다. outbox 멱등성은 DB 중복 등록·동시 전송을 차단하는 범위다.

## 접근 통제

- `notification_outbox` RLS 활성화
- `anon`, `authenticated` table CRUD 없음
- `claim_job_run`, `claim_notification` execute 없음
- D09 등록·payload claim·성공·실패 RPC도 anon/authenticated execute 없음
- 서버 전용 `service_role`만 table CRUD와 claim 함수 execute 가능
- Dashboard 사용자 정책은 G01 전까지 추가하지 않음

## 실DB 검증

- 첫 claim 성공, 활성 상태 즉시 재claim 실패
- 5분 stale job/notification 회수 성공
- attempt 증가 확인
- terminal job·sent notification의 완료 시각 CHECK 확인
- 중복 일기 알림과 멱등 키 거부
- outbox 참조가 남아 있는 일기 삭제 거부
- 임시 검증 데이터 rollback 및 잔여 0건
- 멱등 등록, 중복 claim 거부, 120초 재시도 예약, 두 번째 claim, sent 전환과 provider message ID 기록
- D09 RPC 4개가 invoker·빈 search path·service-role 전용임을 실DB에서 확인
