# E05 기억 버전과 상충 처리

## 구현

- 야간 계약을 schema `1.2.0`, prompt `nightly-v3`, pipeline `nightly-pipeline-v3`로 올리고 기억 후보에 안정 `memoryKey`를 추가했다.
- DB trigger가 category·memory key를 트랜잭션 잠금으로 직렬화한다.
- 동일 사실은 자동 rejected 처리하고, 다른 사실은 기존 행을 가리키는 다음 version pending 후보로 강제한다.
- 사용자가 Telegram에서 확인할 때만 기존 confirmed를 superseded로 전환하고 새 버전을 confirmed로 만든다.

## 검증

- `npm run check`: lint, typecheck, 자동 테스트 200개 통과
- 실제 Groq structured output이 schema `1.2.0`과 `preferred_drink` 안정 키를 반환하고 의미 검증 통과
- 운영 Supabase rollback에서 v1 superseded·중복 rejected·v2 confirmed 상태 전이 확인
- 합성 job·후보 잔존 0건, anon/authenticated RPC 실행 불가, service role만 실행 가능
- 신규 migration `20260927214100 m3_memory_versioning` 적용
