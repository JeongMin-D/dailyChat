# C01 데이터 계약

## 구현

- `@mindcompanion/contracts` workspace package 추가
- JSON Schema Draft 2020-12 기반 event/mood/health/diary/safety 계약
- Groq strict Structured Outputs용 통합 `nightlyExtractionSchema`
- Ajv 8.20.0 고정 버전 runtime 검증
- 입력 snapshot, event 참조, safety 일관성 의미 검증
- 안정적인 `INVALID_NIGHTLY_EXTRACTION` assert 오류
- 야간 프롬프트를 Groq·04:05 final-only·새 계약과 일치시킴

## 핵심 결정

- 모든 객체는 추가 필드를 거부한다.
- strict mode 호환을 위해 모든 필드를 required로 두고 선택 값은 null/빈 배열로 표현한다.
- 파생 데이터와 일기 block은 user 원문 UUID를 하나 이상 근거로 가진다.
- 모델의 source ID는 신뢰하지 않고 실제 입력 snapshot과 대조한다.
- safety에는 등급, 제한 사유 코드, source ID, 검사기 버전만 허용한다.
- Groq strict mode가 지원하지 않는 `uniqueItems`는 schema에서 제외하고 동일한 중복 금지를 의미 검증으로 적용한다.
- 실제 Groq smoke에서 strict shape는 통과했지만 safety 교차 규칙 위반을 확인해 schema 검증과 의미 검증을 분리했다.
- safety를 중첩 `anyOf`로 강제하면 Groq `failed_generation`이 발생해 단순 shape + 저장 전 의미 검증을 채택했다.
- none 등급에서 모델이 반환한 검사 대상 source ID는 snapshot 검증 후 허용하되 DB에는 safety 레코드를 저장하지 않는다.

- 계약 테스트 11개 추가

- 실제 Supabase 스키마는 읽기 전용으로 비교하고 변경하지 않음
- 비밀값과 사용자 원문 fixture 미포함

## 확인된 후속 차이

- legacy `files/schema.sql`의 단일 message ID와 diary content/source 배열은 현재 계약과 다르다.
- C02에서 타입·제약을 표로 확정하고 C03부터 순차 migration을 작성해야 한다.
