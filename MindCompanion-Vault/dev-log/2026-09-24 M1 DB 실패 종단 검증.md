# M1 DB 실패 종단 검증

## 작업 전 확인

- 기준 커밋: `9386950 docs: record retry deployment verification`
- 사용자 변경인 `.obsidian/workspace.json`은 관련 없는 Obsidian 화면 상태로 분류해 보존했다.
- Supabase changelog에서 현재 Data API 관련 breaking change를 확인했다.
- 신규 테이블이나 권한·RLS·운영 데이터 변경은 수행하지 않았다.

## 검증 구성

Telegram webhook HTTP 요청부터 아래 실제 애플리케이션 경계를 모두 연결했다.

1. `createHttpServer`
2. `createConversationService`
3. `SupabaseMessageStore`
4. `GroqProvider`
5. `TelegramClient`

Supabase Data API만 인메모리 fault-injection 응답으로 대체해 PGRST001 HTTP 503을 각 저장 지점에 한 번씩 주입했다.

## 검증 결과

- DB claim 실패: update나 메시지를 만들지 않고 외부 호출 없이 HTTP 500, 다음 전달에서 정상 완료
- user 저장 실패: LLM 호출 전에 중단, `retryable_failed` 기록 후 다음 전달에서 user/assistant 각 1건만 저장
- assistant 저장 실패: Telegram 전송 전에 중단, 다음 전달에서 응답 재생성 후 저장·전송
- 완료 상태 기록 실패: 저장된 assistant 응답을 재사용하고 LLM 중복 호출 방지
- 전체 `npm run check`: lint·typecheck·자동 테스트 49개 통과
- 실제 `npm run smoke:connections`: Supabase 설정 조회 정상, Telegram·Groq 연결 정상

## 공식 문서 확인

- Supabase Data API의 `PGRST001`은 DB 내부 연결 실패를 뜻하는 HTTP 503이다.
- 최신 supabase-js는 일부 PostgREST transient 오류를 자동 재시도하지만, 현재 Bot은 raw fetch adapter이므로 해당 SDK 동작에 의존하지 않는다.
- 서버의 현대식 `sb_secret_` key 사용은 현재 공식 권장 방식과 일치한다.
- 확인일: 2026-09-24

- 출처: `https://supabase.com/docs/guides/getting-started/api-keys`

## 발견된 잔여 위험

Telegram 전송은 성공했지만 이후 DB의 `completed` 기록만 실패하면 update가 `retryable_failed`로 전환된다. 다음 webhook 전달에서 저장된 assistant 응답은 재사용되지만 Telegram 메시지는 다시 전송될 수 있다.

- 리스크 레지스터 `R-13`에 등록
- M1에서는 알려진 제한으로 유지
- M2의 `notification_outbox`와 발송 멱등 키 설계에서 해소
