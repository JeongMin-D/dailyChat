# 원자적 야간 결과 저장

## 목적

D03~D04에서 검증한 구조화 결과를 부모 행만 남거나 근거 일부가 빠지는 상태 없이 저장한다. 여러 Data API insert를 이어 붙이지 않고 PostgreSQL 함수 한 번으로 처리한다.

## 저장 흐름

1. Worker가 output을 snapshot day와 source ID 집합으로 다시 검증한다.
2. `SupabaseNightlyOutputStore`가 `persist_nightly_extraction` RPC를 한 번 호출한다.
3. RPC가 대상 `job_runs` 행을 `FOR UPDATE`로 잠근다.
4. nightly/running 상태, day, schema version, user message 역할과 day를 검사한다.
5. event, mood, health, diary, block, 선택적 safety를 저장한다.
6. 각 부모의 원문 근거와 diary block-event 근거를 연결한다.
7. 모든 저장이 끝난 경우에만 job을 `succeeded`로 전환한다.

## 원자성

- eventRef는 DB에 저장하지 않고 같은 RPC 안에서 생성 event UUID로 해석한다.
- diary block position은 입력 순서대로 0부터 저장한다.
- safety `none`은 행을 만들지 않고 `concern|urgent`만 제한 metadata와 근거를 저장한다.
- constraint, source, event 참조 또는 상태 검증이 하나라도 실패하면 전체 함수 호출이 rollback된다.
- 같은 job의 재호출은 running 상태와 기존 diary 검사를 통과할 수 없다. 완전한 no-op과 변경 입력 version 정책은 D07~D08에서 확정한다.

## 접근 통제

- `SECURITY INVOKER`
- `search_path = ''`
- `public`, `anon`, `authenticated` execute 회수
- `service_role`에만 execute 부여
- service secret은 Worker 서버 환경에서만 사용

## 검증 결과

- 운영 Supabase에 migration 8번째 단계 적용
- 성공 합성 트랜잭션에서 event, mood, health, diary, block, safety 및 근거 연결 각각 1건 확인
- job status가 같은 트랜잭션에서 `succeeded`로 전환됨을 확인
- snapshot day 밖 source ID 실험에서 파생 행 0건과 job `running` 유지 확인
- 모든 합성 검증을 rollback하고 테스트 message/job/diary 0건 확인
- Data API RPC route와 service-role 실행 권한 확인
- public/anon/authenticated execute 없음, invoker와 빈 search path 확인
- Security Advisor 새 ERROR/WARN 없음. 기존 RLS-no-policy INFO는 server-only 정책상 의도된 상태
