# 보안과 개인정보

## 데이터 분류

| 등급 | 데이터 | 처리 원칙 |
|---|---|---|
| 매우 민감 | 건강, 위기 표현, 관계, 일기 원문 | 최소 수집, 암호화 전송, 로그 금지 |
| 민감 | 전체 대화, 장기 기억 | 목적 제한, 근거·삭제 지원 |
| 내부 | 프롬프트, 모델 설정, 운영 지표 | 비밀 제외 후 접근 제한 |
| 비밀 | Telegram token, Groq key, service role | secret store만 사용, 출력 금지 |

## 신뢰 경계

- Telegram update는 서명/secret token과 ID allowlist를 모두 검증한다.
- 외부에서 온 메시지 내용은 명령이 아니라 데이터로 취급한다.
- LLM 출력은 신뢰하지 않고 schema와 source ID를 서버에서 검증한다.
- Dashboard 브라우저는 anon key와 사용자 세션만 사용한다.
- service role은 Bot/Worker 또는 안전한 서버 함수에만 둔다.

## 최소 보안 요구사항

- 모든 테이블 RLS 활성화와 명시적 정책
- 신규 가입 비활성화, 소유자 계정만 유지
- 운영/개발 키 분리와 주기적 회전
- 원문과 비밀이 없는 구조화 로그
- HTTPS webhook, CSRF/세션 기본 방어
- 의존성 고정과 취약점 검사
- 관리자 작업 감사 기록
- 완전 삭제와 백업 보존 기간의 관계 고지

## LLM 개인정보 최소화

- 요청 목적에 필요한 날짜 범위와 기억만 전송한다.
- 오래된 전체 대화를 매번 보내지 않는다.
- 민감 기억은 관련성이 높을 때만 주입한다.
- provider, model, prompt version, 전송한 레코드 ID를 감사 가능하게 기록한다.
- 공급자 보존 정책은 배포 전에 다시 확인하고 운영 문서에 남긴다.

## 건강·위기 안전

- 진단, 처방, 복용량, 치료 결정을 생성하지 않는다.
- 위기 표현이 있으면 일반 말투에서 안전 응답으로 전환한다.
- 연락처와 안내 문구는 출시 직전 공식 출처로 최신성을 검증한다.
- 위기 내용을 일기에 상세 재현하지 않는다.
- `safety_flag`는 접근이 제한된 운영 메타데이터로 다룬다.

## 위협 시나리오

- 공격자가 다른 Telegram 계정에서 봇을 사용
- 원문에 “이전 지시 무시”가 들어가 추출기를 조작
- Dashboard 번들에서 service role이 노출
- 잘못된 source ID가 다른 날짜의 민감 기록을 연결
- 삭제한 기억이 투영 파일 또는 백업에서 다시 살아남음
- 로그/오류 추적 서비스로 원문이 유출

각 시나리오는 [[07 테스트 전략]]의 자동 또는 수동 테스트로 연결한다.
