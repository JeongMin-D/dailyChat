# 보안과 개인정보

## 데이터 분류

| 등급 | 데이터 | 처리 원칙 |
|---|---|---|
| 매우 민감 | 건강, 위기 표현, 관계, 일기 원문 | 최소 수집, 암호화 전송, 로그 금지 |
| 민감 | 전체 대화, 장기 기억 | 목적 제한, 근거·삭제 지원 |
| 내부 | 프롬프트, 모델 설정, 운영 지표 | 비밀 제외 후 접근 제한 |
| 비밀 | Telegram token, Groq key, service role | secret store만 사용, 출력 금지 |

## 신뢰 경계

- Telegram update는 서명/secret token과 ID allowlist를 모두 검증한다.
- 외부에서 온 메시지 내용은 명령이 아니라 데이터로 취급한다.
- LLM 출력은 신뢰하지 않고 schema와 source ID를 서버에서 검증한다.
- Dashboard 브라우저는 anon key와 사용자 세션만 사용한다.
- service role은 Bot/Worker 또는 안전한 서버 함수에만 둔다.

## 최소 보안 요구사항

- 모든 테이블 RLS 활성화와 명시적 정책
- 신규 가입 비활성화, 소유자 계정만 유지
- 운영/개발 키 분리와 주기적 회전
- 원문과 비밀이 없는 구조화 로그
- HTTPS webhook, CSRF/세션 기본 방어
- 의존성 고정과 취약점 검사
- 관리자 작업 감사 기록
- 완전 삭제와 백업 보존 기간의 관계 고지

## 보존 기간

세부 결정은 [[decisions/ADR-012 개인정보 보존 기간]]을 따른다.

| 데이터 | 보존 기간 | 이유 |
|---|---|---|
| 원문 대화·일기·event·mood·health | 사용자가 완전 삭제하거나 서비스를 종료할 때까지 | 장기 일기와 근거 추적이라는 본래 목적 |
| confirmed·forgotten 기억과 근거 | 사용자가 완전 삭제할 때까지 | 활성 집합과 정정·삭제 이력의 감사 가능성 |
| pending·rejected 기억 후보 | 결정 또는 생성 후 최대 30일 | 불필요한 민감 후보 최소화 |
| 종료된 job·notification·Telegram 처리 원장 | 최대 90일, 보존 콘텐츠가 참조하면 참조 종료까지 | 장애 추적과 중복 방지 |
| 원문 없는 애플리케이션 로그 | 최대 30일 | 장애 조사에 필요한 최소 기간 |
| `MEMORY.md`와 런타임 캐시 | 다음 재생성 즉시 교체, 별도 백업 금지 | Supabase 원장의 파생물 |
| 자체 암호화 DB 백업 | 최대 30일 | 무료 플랜 복구와 삭제 이행의 균형 |

보존 기간은 자동 삭제 기능이 구현되기 전까지 상한으로 사용한다. 기간이 지난 데이터를 계속 보관하는 운영은 허용하지 않으며, 자동 정리는 삭제 영향 처리와 복구 검증을 통과한 뒤 활성화한다.

## 삭제 수준

- `잊어줘`: 기억을 즉시 비활성화해 Bot과 투영에서 제외하지만 감사 이력은 보존한다.
- 완전 삭제: 원문과 관련 파생 데이터·근거·투영·캐시를 함께 제거한다.
- 완전 삭제 후에는 삭제 전 자체 백업을 폐기하고 삭제 후 상태로 새 백업을 만든다.
- 공급자 백업에 삭제 데이터가 남을 수 있는 기간은 사용자에게 고지하고, 복구 시 삭제 데이터를 운영 DB에 다시 반입하지 않는다.

## LLM 개인정보 최소화

- 요청 목적에 필요한 날짜 범위와 기억만 전송한다.
- 오래된 전체 대화를 매번 보내지 않는다.
- 민감 기억은 관련성이 높을 때만 주입한다.
- provider, model, prompt version, 전송한 레코드 ID를 감사 가능하게 기록한다.
- 공급자 보존 정책은 배포 전에 다시 확인하고 운영 문서에 남긴다.

## 건강·위기 안전

- 진단, 처방, 복용량, 치료 결정을 생성하지 않는다.
- 위기 표현이 있으면 일반 말투에서 안전 응답으로 전환한다.
- 연락처와 안내 문구는 출시 직전 공식 출처로 최신성을 검증한다.
- 위기 내용을 일기에 상세 재현하지 않는다.
- safety level·제한 사유 코드·근거 ID는 접근이 제한된 운영 메타데이터로 다룬다.
- safety `none`은 DB에 저장하지 않으며 concern/urgent에도 원문 인용·진단명·자유 형식 판단을 저장하지 않는다.
- safety 테이블은 service role만 접근하고 Dashboard 소유자 정책이 준비되기 전에는 사용자 세션에 열지 않는다.

## 위협 시나리오

- 공격자가 다른 Telegram 계정에서 봇을 사용
- 원문에 “이전 지시 무시”가 들어가 추출기를 조작
- Dashboard 번들에서 service role이 노출
- 잘못된 source ID가 다른 날짜의 민감 기록을 연결
- 삭제한 기억이 투영 파일 또는 백업에서 다시 살아남음
- 로그/오류 추적 서비스로 원문이 유출

각 시나리오는 [[07 테스트 전략]]의 자동 또는 수동 테스트로 연결한다.
