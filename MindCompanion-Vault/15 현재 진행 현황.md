## C02 DB 정합성 결과

- JSON Schema 모든 필드를 PostgreSQL 컬럼·관계·transient 값으로 분류했다.
- UTC 시각 `timestamptz`, local day `date`, confidence `numeric(5,4)`를 기준 타입으로 정했다.
- 원문과 파생 데이터는 유형별 연결 테이블과 복합 PK/FK로 연결한다.
- 원문 삭제는 영향 처리 전까지 restrict하고, 파생 부모 삭제 시 연결 행만 cascade한다.
- RLS 활성화, `anon`/`authenticated` 회수, `service_role` 명시 grant를 migration 공통 규칙으로 유지한다.
- C02 시점에는 운영 DB를 변경하지 않았고, C03에서 core domain과 근거 관계를 적용했다.

## C03 근거 스키마 결과

- `events`, `mood_entries`, `health_entries`, `diaries`, `diary_blocks`를 생성했다.
- event/mood/health/diary block 원문 근거와 diary block-event 근거 연결 테이블 5개를 생성했다.
- 모든 새 테이블에 RLS를 켜고 `anon`/`authenticated` 권한을 회수했으며 `service_role` CRUD만 명시했다.
- 복합 PK, FK, enum·범위·길이 CHECK와 cascade/restrict 삭제 정책을 실DB에서 확인했다.
- 정상 저장, 중복 근거 거부, 잘못된 confidence 거부, 참조 원문/event 삭제 거부를 임시 트랜잭션으로 검증하고 전부 롤백했다.
- Security Advisor의 정책 없음 INFO는 클라이언트 권한이 없는 server-only 단계의 의도된 상태이며 Dashboard 정책은 G01에서 추가한다.

## C05 안전과 재현 메타데이터 결과

- nightly job에 day, pipeline/input hash, provider/model, prompt/schema version을 필수화했다.
- input hash는 lowercase SHA-256 hex 형식만 허용한다.
- safety는 `concern|urgent`만 저장하며 `none`은 저장하지 않는다.
- safety 원장에는 제한 사유 코드, checker version, 판정 시각과 원문 FK만 둔다.
- 원문 인용, 진단명, 자유 형식 추론, 일기·건강 본문 컬럼이 없음을 실DB 카탈로그로 확인했다.
- 잘못된 hash·등급·사유·빈 사유·중복 판정·중복 근거와 참조 원문 삭제가 거부됨을 확인했다.

## C06 시간 경계 무결성 결과

- Supabase DB timezone이 UTC이고 운영 설정이 `Asia/Seoul`, 경계 04시, final 04:05인지 확인했다.
- Telegram Unix timestamp가 앱에서 UTC `Date`로 유지되고 03:59:59/04:00:00 KST에 서로 다른 local day로 저장됨을 테스트했다.
- `messages.sent_at`과 supplied `day`를 설정 기반 `local_day()`와 대조하는 trigger를 적용했다.
- 올바른 경계 행 저장과 UTC round-trip, 잘못된 insert/update 거부를 운영 DB 트랜잭션에서 검증하고 롤백했다.
- trigger 함수는 `SECURITY INVOKER`, 빈 `search_path`, 모든 Data API 역할 직접 실행 불가 상태다.
- 테스트 데이터가 0건 남았고 Security Advisor에 새 ERROR/WARN이 없음을 확인했다.

## D01~D02 야간 입력 Snapshot 결과

- Scheduler가 현재 열린 날짜가 아니라 마지막으로 완전히 닫힌 local day를 선택한다.
- 재시도와 늦은 실행은 계산을 반복하지 않고 명시된 job day를 사용한다.
- Supabase에서 해당 day의 user message만 `sent_at`, `id` 오름차순과 pagination으로 읽는다.
- Snapshot은 version/day와 `id`, UTC `sentAt`, `content`만 포함해 canonical UTF-8 JSON으로 직렬화한다.
- Snapshot 전체에 lowercase SHA-256을 적용하며 순서와 timestamp 표기가 달라도 같은 입력은 같은 hash를 만든다.
- 실제 2026-09-24 user 메시지 5건을 두 번 읽어 DB count, snapshot, hash 일치를 확인했다.
- 원문 snapshot은 Worker 메모리에만 두고 hash만 job 재현 정보로 사용한다.

## D03~D04 구조화 추출과 검증 결과

- Groq `openai/gpt-oss-120b`에 strict JSON Schema로 구조화 결과를 요청한다.
- 원문 JSON은 신뢰하지 않는 자료로 격리하고 내부 지시를 따르지 않도록 `nightly-v1` system prompt를 고정했다.
- Ajv shape 뒤에 snapshot day, source ID 소속, event 참조, 중복 배열, safety 근거의 의미 검증을 수행한다.
- 잘못된 JSON 또는 의미 검증은 원문·잘못된 값 없이 경로와 오류 종류만 전달해 최대 한 번 교정한다.
- 빈 입력은 Groq 호출 없이 skip하고, refusal·HTTP·두 번째 검증 실패는 안정적인 오류 코드로 종료한다.
- 합성 입력 실제 Groq smoke가 1회 호출로 schema/source 검증을 통과했다. 실제 사용자 원문 전송 smoke는 명시적 외부 전송 승인 전까지 실행하지 않았다.
- 전체 lint·typecheck·자동 테스트 115개가 통과했다.

## D05~D06 원자적 야간 결과 저장 결과

- `persist_nightly_extraction` RPC 하나에서 job row를 잠그고 event, mood, health, diary, block, safety와 모든 근거 연결을 저장한다.
- RPC는 `SECURITY INVOKER`, 빈 `search_path`, `service_role` 전용 execute 권한으로 적용했다.
- Worker store가 snapshot 기준으로 결과를 다시 검증한 뒤 단 한 번의 Data API 요청만 보낸다.
- DB도 job day/schema와 모든 source message의 user 역할·day를 다시 대조하고 eventRef를 같은 트랜잭션에서 실제 event ID로 해석한다.
- 운영 DB 합성 데이터 rollback 검증에서 모든 도메인·근거 행이 각각 생성되고 job이 succeeded로 전환됐다.
- 잘못된 source ID는 파생 행 0건, job running 상태로 전체 rollback됐으며 테스트 데이터는 0건 남았다.
- 실제 Data API RPC 경로가 service role에서 도달 가능하고, anon/authenticated/public 실행 권한은 없음을 확인했다.
- 전체 lint·typecheck·자동 테스트 124개가 통과했다.

## D07~D08 야간 재실행과 일기 버전 결과

- `prepare_nightly_job`이 `day + pipeline_version + input_hash` 고유 job을 만들거나 기존 상태를 반환한다.
- 같은 입력의 성공 job은 기존 diary ID/version과 `noop`을 반환해 Groq 호출 전에 종료할 수 있다.
- 같은 identity에 provider/model/prompt/schema metadata가 달라지면 pipeline version 변경을 요구하며 거부한다.
- 변경된 input hash는 새 job을 생성하고 날짜별 advisory transaction lock 안에서 다음 diary version을 계산한다.
- 성공 job의 저장 재호출도 기존 diary를 반환하므로 부모·근거가 중복 저장되지 않는다.
- 운영 DB rollback 검증에서 첫 입력 version 1, 변경 입력 version 2, 같은 입력 prepare/save no-op을 확인했다.
- 신규 RPC는 invoker, 빈 search path, service-role 전용이며 실제 Data API 경로가 정상이다.
- 합성 message/job/diary는 모두 rollback되어 0건 남았다.
- 전체 lint·typecheck·자동 테스트 130개가 통과했다.

## D09 Telegram 일기 Outbox 결과

- succeeded job과 diary 참조를 운영 chat ID에 멱등 등록하며 outbox에 일기 본문을 저장하지 않는다.
- due 알림 claim 시에만 diary와 순서가 있는 block을 읽어 transient payload를 반환한다.
- Telegram 일반 텍스트를 4,096자 안으로 구성하고 성공 `message_id`를 outbox에 기록한다.
- 429·5xx·네트워크 오류는 최대 5회 지수 backoff하고, `retry_after`가 더 길면 우선한다.
- 401·403과 그 밖의 4xx, 최대 attempt 도달은 영구 실패로 기록한다.
- 운영 DB rollback 검증에서 멱등 등록, 중복 claim 거부, retry 예약, 두 번째 claim과 sent 전환을 확인했다.
- 합성 job/diary/outbox 잔존은 모두 0건이고, 신규 RPC는 invoker·빈 search path·service-role 전용이다.
- 실제 Telegram 채팅에는 테스트 메시지를 보내지 않았다.
- 전체 lint·typecheck·자동 테스트 144개가 통과했다.
