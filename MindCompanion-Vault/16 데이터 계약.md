# 데이터 계약

## 기준

C01 계약의 코드 원본은 `packages/contracts/src/schemas.js`다. JSON Schema Draft 2020-12를 사용하며 Groq strict Structured Outputs 요구사항에 맞춰 모든 필드를 required로, 모든 객체를 `additionalProperties: false`로 정의한다. nullable 값은 필드를 생략하지 않고 `null`로 반환한다.

## 야간 추출 결과

| 영역 | 핵심 필드 | 제약 |
|---|---|---|
| 공통 | `schemaVersion`, `day` | 버전 `1.0.0`, local day `YYYY-MM-DD` |
| event | `eventRef`, `type`, `summary`, `occurredAt`, `confidence`, `sourceMessageIds` | type enum, confidence 0~1, 근거 1개 이상 |
| mood | `score`, `label`, `source`, `confidence`, `sourceMessageIds` | score 1~5, source inferred/checkin |
| health | `symptom`, `severity`, `note`, `occurredAt`, `confidence`, `sourceMessageIds` | severity null 또는 1~3 |
| safety | `level`, `reasonCodes`, `sourceMessageIds`, `checkerVersion` | none/concern/urgent, 제한 코드만 저장 |
| diary | `title`, `summaryMood`, `tags`, `blocks` | block마다 직접 원문 근거 1개 이상 |

## 근거 검증

JSON Schema 통과만으로 저장하지 않는다. `validateNightlyExtraction`이 다음 의미 규칙도 검사한다.

- `eventRef`는 결과 안에서 유일해야 한다.
- 일기 `sourceEventRefs`는 같은 결과의 event만 가리켜야 한다.
- 모든 `sourceMessageIds`는 Worker가 전달한 user 메시지 snapshot에 실제 존재해야 한다.
- 출력 `day`는 입력 snapshot의 명시된 day와 정확히 같아야 한다.
- safety가 none이면 사유 코드는 비어 있어야 한다. 검사 대상으로 반환된 source ID는 snapshot 대조 후 허용하되 DB safety 레코드는 저장하지 않는다.
- safety가 concern/urgent이면 사유와 근거가 모두 있어야 한다.
- 일기 block마다 user 원문 근거가 하나 이상 있어야 한다.
- Groq strict mode가 지원하지 않는 `uniqueItems` 대신 배열 중복을 의미 검증에서 거부한다.

Groq strict schema는 출력 shape를 보장하지만 snapshot 소속, 참조 존재, 안전 등급과 근거의 교차 규칙까지 보장하지 않는다. 실제 smoke를 통해 이 차이를 확인했다. 중첩 `anyOf`로 safety 규칙을 강제하는 방식은 Groq `failed_generation`을 유발해 채택하지 않았으며, 단순 shape 뒤에 로컬 의미 검증을 적용한다.

이 규칙은 [[decisions/ADR-004 원문과 파생 데이터 근거]], [[decisions/ADR-006 안전 플래그 저장과 알림]]을 구현한다.

## 실행 경로

`workers/nightly/src/nightly-extractor.js`가 D03~D04 계약을 실행한다.

1. canonical snapshot이 비어 있으면 외부 호출 없이 skip한다.
2. `nightly-v1` prompt와 strict `nightlyExtractionSchema`로 Groq를 호출한다.
3. JSON parse 후 Ajv shape와 로컬 의미 규칙을 모두 검사한다.
4. 실패 시 검증 경로·keyword·일반 오류 메시지만 전달해 한 번 교정한다. source UUID를 포함한 params와 원문·잘못된 출력은 교정 메시지와 로그에서 제외한다.
5. 재실패는 `INVALID_NIGHTLY_EXTRACTION`, refusal과 HTTP 실패는 별도 안정적 코드로 종료한다.

## 현재 DB 반영 상태

`0004_core_domain_sources.sql`이 `events`, `mood_entries`, `health_entries`, `diaries`, `diary_blocks`와 유형별 근거 연결 테이블을 운영 Supabase에 적용했다. `files/schema.sql`은 제안서 참고본일 뿐이며 다음 부분은 현재 계약에서 대체되었다.

- 단일 `message_id` 대신 유형별 다대다 근거 테이블 필요
- 일기 단일 content/source 배열 대신 순서 있는 근거 block 필요
- boolean safety flag 대신 등급·제한 사유·검사기 버전 필요
- model/prompt/schema/pipeline version과 input hash 저장 필요

C02에서 컬럼·enum·null·범위, FK와 삭제 정책을 [[17 DB 정합성 명세]]로 확정했고 C03 core domain migration에 반영했다. C04에서는 [[18 작업과 알림 원장]], C05에서는 [[19 안전과 재현 메타데이터]]와 공유 재현 계약을 적용했다. 실행 가능한 계약은 `packages/contracts/src/`에 있다. Worker 저장 로직이 완성되기 전까지 운영 파생 데이터 생성은 시작하지 않는다.

## 검증

- Ajv 8.20.0 Draft 2020-12 strict compile
- Groq strict subset 검사와 실제 API smoke test
- 정상 fixture와 개별 event/mood/health/diary/safety 계약
- 추가 필드, 잘못된 enum·범위·UUID 거부
- 근거 없는 일기, snapshot 밖 ID, 존재하지 않는 event 참조 거부

## 야간 입력 Snapshot

실행 가능한 계약은 `nightlyInputSnapshotContract`와 `workers/nightly/src/nightly-input.js`다.

- scheduler는 마지막으로 완전히 닫힌 local day를 선택하고 job에 명시한다.
- Worker는 명시된 day의 user message만 사용한다.
- canonical message 필드는 `id`, UTC ISO `sentAt`, `content`다.
- 정렬은 `sentAt` 오름차순 후 `id` 오름차순이다.
- snapshot version/day/messages를 고정 필드 순서의 UTF-8 JSON으로 직렬화한다.
- lowercase SHA-256 hash는 source ID, timestamp, content 또는 day가 바뀌면 달라진다.
- 원문 snapshot은 DB job row에 복제하지 않는다.
- 안전 등급과 근거 불일치 거부
- JSON Schema의 모든 필드에 DB 저장·관계·transient 분류가 존재하는지 자동 대조
- enum, 수치 범위, nullable, 원문 FK 관계, 역할 권한 정책 대조
