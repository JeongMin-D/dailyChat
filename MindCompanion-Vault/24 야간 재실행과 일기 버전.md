# 야간 재실행과 일기 버전

## job identity

야간 job의 고유 identity는 다음 네 필드다.

`nightly + day + pipeline_version + input_hash`

- 같은 day, pipeline, input hash는 같은 job이다.
- input hash가 바뀌면 늦게 도착한 메시지가 포함된 새 job이다.
- 모델·프롬프트·schema 변경은 pipeline version도 함께 바꿔야 한다.

## prepare 결과

| action | 의미 | Worker 처리 |
|---|---|---|
| `created` | 새 identity | claim 후 추출 진행 |
| `noop` | 동일 입력이 이미 성공 | 기존 diary를 사용하고 Groq 호출 생략 |
| `resume` | queued 또는 retryable_failed | claim 후 재시도 |
| `in_progress` | 다른 실행이 처리 중 | 중복 처리하지 않음 |
| `terminal_failed` | 영구 실패 | 자동 재실행하지 않음 |

## version 정책

- 첫 성공 일기는 version 1이다.
- 변경 input hash의 새 성공 결과는 같은 day의 `max(version) + 1`이다.
- 이전 diary와 파생 데이터는 보존한다.
- version 계산과 저장은 같은 트랜잭션이다.
- 날짜별 advisory transaction lock으로 동시 저장의 같은 version 할당을 직렬화한다.
- 같은 성공 job의 저장 재호출은 `noop`과 기존 diary를 반환한다.

## 재현성 보호

동일 job identity로 prepare할 때 provider, model, prompt version, schema version이 기존 row와 모두 같아야 한다. 하나라도 다르면 기존 성공 결과를 재사용하지 않고 pipeline version 변경을 요구한다.

## 검증 결과

- 운영 Supabase migration 9번째 단계 적용
- 첫 prepare `created`, 첫 저장 `saved`, 동일 입력 prepare `noop`
- 변경 hash prepare `created`, 저장 후 diary version `[1, 2]`
- 두 번째 job 저장 재호출 `noop`
- 같은 날짜 job 2개 모두 succeeded
- 합성 검증은 전체 rollback, 테스트 message/job/diary 잔존 0건
- prepare/save RPC 모두 invoker, 빈 search path, service-role 전용 실행
- Data API RPC 두 경로 도달 확인
- Security Advisor 새 ERROR/WARN 없음
