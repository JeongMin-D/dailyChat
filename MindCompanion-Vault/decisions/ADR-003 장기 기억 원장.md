# ADR-003 — 장기 기억 원장

## 상태

승인

## 배경

장기 기억을 Agent 파일과 Supabase 양쪽에서 수정할 수 있으면 충돌 시 어떤 값이 진실인지 알 수 없고, “잊어줘” 요청과 변경 이력을 완전하게 적용하기 어렵다. Dashboard와 Bot도 같은 기억 상태를 읽어야 한다.

## 선택지

1. `MEMORY.md` 같은 Agent 파일을 원본으로 사용하고 DB에 복제
2. Supabase를 원장으로 사용하고 Agent 파일은 생성된 투영본으로 사용
3. DB와 파일의 양방향 동기화 및 충돌 병합

## 결정

Supabase PostgreSQL을 장기 기억의 유일한 영속 원장으로 사용한다. 기억의 상태, 버전, 근거, 유효 기간, 정정과 삭제 이력을 DB에 저장한다. `MEMORY.md`와 `USER.md`는 활성 기억에서 재생성하는 읽기 전용 투영본이며 직접 편집한 내용을 DB로 역수입하지 않는다. 충돌하거나 투영 생성이 실패하면 DB가 우선한다.

Bot과 Worker의 쓰기는 서버 전용 secret key로 수행하고 브라우저에는 공개하지 않는다. Dashboard를 열 때는 publishable key, Supabase Auth, 소유자 RLS 정책을 함께 사용한다. Data API 접근은 플랫폼의 자동 노출 기본값에 기대지 않고 migration에서 grant와 RLS를 명시한다.

## 결과

- 장점: 기억 수정·비활성화·삭제와 감사 이력을 한 곳에서 보장하고 모든 소비자가 같은 상태를 읽는다.
- 단점: Agent가 파일만 수정하는 기능은 사용할 수 없고 투영 재생성·캐시 무효화가 필요하다.
- 후속 작업: 기억 원장과 변경 이력 스키마, 투영 버전/hash, 삭제 후 재생성, Dashboard 소유자 RLS를 구현한다.

## 검증 방법

- 기억 추가·정정·상충·비활성화·삭제 뒤 Bot과 투영 파일이 같은 활성 집합을 반환하는지 확인한다.
- 삭제된 기억이 투영 재생성과 캐시 갱신 뒤 다시 나타나지 않는지 테스트한다.
- `anon`과 비소유자 접근은 차단되고 소유자 세션만 허용되는지 RLS 부정 테스트를 수행한다.
