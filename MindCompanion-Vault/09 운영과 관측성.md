# 운영과 관측성

## HTTP 요청 추적

- 유효한 `X-Request-ID`가 있으면 유지하고, 없거나 잘못된 값이면 UUID를 생성한다.
- 응답 헤더와 오류 본문에 동일한 request ID를 반환한다.
- webhook 처리 오류와 HTTP 완료 로그를 동일한 request ID로 연결한다.
- 오류 응답은 `error.code`, `error.message`, `error.requestId` 구조를 사용한다.

## 로그 형식

- 한 줄 JSON으로 `timestamp`, `level`, `service`, `event`를 기록한다.
- 사용자 원문과 토큰·secret·authorization·API key 필드는 자동 마스킹한다.
- 내부 예외 메시지는 외부 응답에 노출하지 않고 안정적인 오류 코드로 변환한다.

## 작업 상태

야간 처리와 알림은 상태를 분리한다.

```text
job_run: queued → running → succeeded | retryable_failed | failed
notification: pending → sending → sent | retryable_failed | failed
```

각 실행은 `run_id`, `day`, `input_hash`, `attempt`, `model`, `prompt_version`, `started_at`, `finished_at`, `error_code`를 가진다.

## 재시도 정책

- 429/일시적 5xx/네트워크 오류: 지수 backoff + jitter
- 잘못된 JSON/source ID: 교정 프롬프트 1회 후 실패
- 인증/권한/스키마 오류: 자동 재시도 금지, 즉시 알림
- Telegram 발송 실패: 일기 생성은 성공으로 유지하고 발송만 재시도
- 모든 재시도는 멱등 키를 사용한다.

## 관측 지표

- Telegram update 수신/처리/중복/차단 건수
- 대화 LLM 지연, 오류율, 토큰 사용량
- 야간 작업 성공률과 소요 시간
- 추출 결과 수와 validation 실패율
- 일기 생성 및 전송 성공률
- 근거 없는 source ID 발생 수
- 사용자 👍/👎 비율
- DB 크기와 백업 성공/복구 시간

## 알림 기준

- 야간 final이 예정 시간 이후 30분 안에 생성되지 않음
- 연속 LLM 오류 또는 rate limit 임계 초과
- Telegram webhook 처리 실패 누적
- 백업 실패
- RLS/인증 관련 오류
- 비용 또는 토큰 사용량 급증

알림에는 원문, 건강 정보, 일기 내용을 넣지 않는다.

## 백업과 복구

- 일일 자동 백업과 보존 기간 설정
- 프롬프트·migration·구성은 저장소 버전으로 보존
- 비밀은 백업 파일에 포함하지 않고 별도 복구 절차 유지
- 최소 월 1회 빈 환경 복구 리허설
- 복구 후 레코드 수, 최신 일기, 기억 상태, RLS를 검증

## 비용 관리

MVP 초기에는 품질 기준 모델 하나로 안정화한 뒤, 고정 골든셋에서 품질이 유지될 때만 추출 작업을 경량 모델로 이동한다. 모델별 입력/출력 토큰과 작업별 비용을 기록해 실제 데이터로 결정한다.
