# 핵심 데이터 흐름

## 실시간 대화

```text
Telegram update
 → update_id / chat_id 검증
 → 허용 사용자 확인
 → 사용자 메시지 INSERT (멱등)
 → 관련 확정 기억 + 최근 대화 조회
 → 최소 컨텍스트로 LLM 호출
 → assistant 메시지 INSERT
 → Telegram 응답 전송
```

### 실패 원칙

- DB 저장 전에는 LLM을 호출하지 않는다.
- 같은 Telegram update가 다시 와도 한 번만 처리한다.
- LLM 실패 시 원문은 남기고 짧은 오류 응답과 재처리 상태를 기록한다.
- Telegram 발송 실패는 생성 결과와 분리해 재시도한다.

## 하루 처리

[[decisions/ADR-002 하루 일기 확정 시점]]에 따라 MVP는 **04:05 final-only**로 운영한다.

```text
다음 날 04:05 KST
 → 전날 local day 입력 동결
 → events / mood / health 추출
 → 근거 ID 검증
 → final diary 생성
 → 버전 및 input_hash 저장
 → Telegram final 전송
```

23:30 draft와 미리보기 발송은 MVP 이후 선택 기능으로 남긴다.

## 구조화 추출과 근거

```text
messages
   │
   ├─ event_message_sources ─ events
   ├─ health_message_sources ─ health_entries
   └─ mood_message_sources ─ mood_entries

events ─ diary_event_sources ─ diaries
messages ─ diary_message_sources ─ diaries  # 사건이 없는 근거 보완
```

LLM이 반환한 모든 source ID는 해당 날짜 입력에 실제 존재하는지 서버가 검증한다. 존재하지 않는 ID가 있으면 저장하지 않고 한 번 교정 요청한 뒤 작업을 실패 처리한다.

근거 관계와 일기 근거 단위의 세부 원칙은 [[decisions/ADR-004 원문과 파생 데이터 근거]]를 따른다.

## 기억 수명주기

```text
message/event
 → memory_candidate
 → confidence와 근거 검증
 → 필요 시 사용자 확인
 → active memory
 → 대화 컨텍스트에 제한적으로 사용
 → 수정 / 비활성화 / 삭제
 → Agent용 MEMORY.md 재생성
```

기억에는 최소한 `status`, `fact`, `category`, `confidence`, `source IDs`, `valid_from`, `valid_to`, `updated_at`이 필요하다.

## 검색

MVP 검색 순서:

1. 날짜 범위 해석
2. 키워드 및 `pg_trgm` 검색
3. 이벤트·일기·원문을 유형별로 반환
4. 결과에 날짜, 요약, 근거 링크 표시

자연어 질의의 LLM 해석은 읽기 전용 검색 파라미터로만 사용하며 임의 SQL을 생성·실행하지 않는다.

## 삭제와 수정

- 원문 수정은 기본적으로 새 정정 레코드로 남기고 UI에 최신 상태를 표시한다.
- 사용자의 완전 삭제 요청은 파생 이벤트·일기 근거·기억 투영까지 영향을 계산한다.
- 삭제 후 영향을 받은 일기는 `stale`로 표시하고 재생성 여부를 선택하게 한다.
