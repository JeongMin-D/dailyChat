# DB 정합성 명세

## 목적과 기준 원본

C02는 [[16 데이터 계약]]의 JSON 필드를 PostgreSQL 저장 구조에 일대일로 분류한다. 실행 가능한 기준 원본은 `packages/contracts/src/database-contract.js`이며 이 문서는 사람이 검토하기 위한 요약이다.

C02에서는 운영 DB를 변경하지 않았다. C03에서 core domain과 근거 관계를 구현했고 C04에서 작업 claim과 알림 outbox를 적용했다. C05에서 safety·재현 metadata를 이어서 적용한다.

## 공통 타입

| 애플리케이션 의미 | PostgreSQL | 규칙 |
|---|---|---|
| ID | `uuid` | `gen_random_uuid()` 기본값 |
| local day | `date` | KST 04:00 경계를 애플리케이션에서 계산 |
| 실제 시각 | `timestamptz` | UTC로 저장하고 표시에만 timezone 적용 |
| confidence | `numeric(5,4)` | NOT NULL, 0 이상 1 이하 |
| 점수·severity | `smallint` | mood 1~5, health null 또는 1~3 |
| 제한 문자열 | `text` | NOT NULL/NULL과 길이 CHECK를 계약대로 구분 |
| 일반 태그 배열 | `text[]` | 빈 배열 기본값, 최대 개수는 DB CHECK |
| 원문·event 근거 | 연결 테이블 | 배열/JSON 컬럼으로 저장하지 않음 |

## 출력 필드 매핑

| JSON 영역 | 저장 대상 | 핵심 제약 |
|---|---|---|
| `schemaVersion`, `day` | `job_runs.schema_version`, `job_runs.day` | version `1.0.0`, day NOT NULL |
| `events[]` | `events` | type enum, summary 1~500, nullable `occurred_at`, confidence 0~1 |
| `moods[]` | `mood_entries` | score 1~5, source enum, confidence 0~1 |
| `healthEntries[]` | `health_entries` | symptom 1~120, nullable severity/note/occurred_at |
| `safety` | `safety_assessments` | `concern|urgent`만 저장, 제한 사유와 checker version |
| `diary` | `diaries` | day/version unique, title·summary·tags 제약 |
| `diary.blocks[]` | `diary_blocks` | diary 안 position unique, text 1~1000 |
| `eventRef` | 저장하지 않음 | 같은 트랜잭션의 event ID 해석에만 사용 |

## 근거 연결

다음 연결 테이블은 부모 ID와 source ID를 복합 PK로 사용한다.

- `event_message_sources`
- `mood_message_sources`
- `health_message_sources`
- `safety_message_sources`
- `diary_block_message_sources`
- `diary_block_event_sources`

파생 부모를 지우면 연결 행은 `ON DELETE CASCADE`로 함께 정리한다. 반대로 source message/event 삭제는 `ON DELETE RESTRICT`로 막는다. 삭제 요청은 영향을 받는 파생 행을 먼저 삭제하거나 stale 처리한 후 원문을 삭제하는 명시적 흐름으로 구현한다.

## DB와 애플리케이션의 책임 경계

DB가 직접 강제한다.

- NOT NULL, enum, 길이, 수치 범위, 배열 개수
- PK, unique, FK와 삭제 정책
- `diaries(day, version)`, `diary_blocks(diary_id, position)` 유일성
- 모든 테이블 RLS와 역할별 명시 권한

저장 전 애플리케이션 검증과 한 트랜잭션이 강제한다.

- source ID가 해당 run day의 user message snapshot에 속하는지
- eventRef가 같은 LLM 결과의 event를 가리키는지
- 배열 원소와 source ID 중복 금지
- 모든 파생 부모가 최소 한 개 이상의 원문 근거를 갖는지
- safety `none`은 저장하지 않고 `concern|urgent`만 제한 메타데이터로 저장
- 파생 부모와 모든 근거 연결의 원자적 저장

## 접근 통제

Supabase의 새 테이블 자동 노출 여부에 의존하지 않는다.

- `public`의 모든 새 테이블에 RLS 활성화
- `anon`, `authenticated`의 table 권한 명시 회수
- 서버 전용 `service_role`에 필요한 CRUD만 명시 grant
- service secret은 Bot/Worker 환경에서만 사용
- Dashboard 소유자 정책은 별도 migration과 부정 테스트가 준비되기 전까지 열지 않음

## C03 검증 결과

- [x] target core 테이블 5개와 연결 테이블 5개 생성
- [x] 타입·CHECK·unique·FK·delete 규칙 카탈로그 확인
- [x] 존재하지 않는 원문·중복 연결·잘못된 범위 거부 확인
- [x] RLS와 역할별 권한 실DB 확인
- [x] 자동 테스트 70개와 migration dry-run 통과
- [x] Security/Performance Advisor 검토

Advisor의 `rls_enabled_no_policy` INFO는 현재 `anon`과 `authenticated`의 table 권한을 모두 회수한 server-only 단계이므로 의도된 상태다. Dashboard 사용자 정책은 G01에서 소유자 부정 테스트와 함께 추가한다. 새 인덱스의 unused INFO는 적용 직후 아직 야간 파이프라인 트래픽이 없어 발생한 것으로, D05 이후 실제 쿼리 패턴과 함께 재검토한다.
